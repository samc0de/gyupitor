### 1. BigQuery Analysis: Uncovering Cost Savings

Our deep dive into the `tlabs-finops` project's BigQuery usage over the past 30 days yielded some crucial insights. We identified a single, highly repetitive query pattern as the primary cost driver, responsible for scanning over 350 GB per month. This query consistently performed full table scans and repetitive subqueries.

**Our key recommendations to optimize this:**

*   **Partition and Cluster the Source Table:** This is the most impactful recommendation, enabling BigQuery to scan only relevant data blocks.
*   **Refactor the SQL Query:** Eliminate inefficient subqueries and leverage BigQuery's partitioning features (like `_PARTITIONTIME`).
*   **Materialize Latest Data:** For frequently accessed "latest" data, creating a smaller, dedicated table can drastically reduce scan sizes.

Implementing these optimizations for just this one query pattern could lead to a **>96% reduction in data scanned** and significant cost savings, highlighting a powerful opportunity if applied across similar patterns.

### 2. Architecture Design: A Serverless and Scalable Solution

We've designed a lean, serverless architecture on Google Cloud Platform (GCP) to continuously monitor and report on BigQuery cost optimization opportunities.

**Regarding your question, "Where is the server running?":**

Our application is designed to be **entirely serverless**. This means you won't have traditional dedicated servers running constantly. Instead, we leverage GCP services that scale automatically and only consume resources when active:

*   **Cloud Run Jobs (Analyzer):** This is where the core analysis logic runs. It's a containerized Python application that executes on demand when triggered by the scheduler. It spins up, performs its task, and then shuts down, meaning you only pay for the computation time used.
*   **Cloud Run Service (API):** This is a lightweight, containerized FastAPI application that provides an HTTP endpoint for the UI to fetch findings. It automatically scales up or down to zero instances based on demand.
*   **BigQuery:** This serves as both the source of raw usage data (`INFORMATION_SCHEMA`) and the sink for our processed findings.
*   **Cloud Scheduler:** This acts as a cron job, triggering the analysis job periodically (e.g., daily).

This serverless approach provides high scalability, reliability, and cost efficiency, as you're not paying for idle server time.
